## Wire proposal

Use a new `explanation_contract_version: 3` (or a separately versioned sidecar if the owner prefers) and distinct method `lightgbm_pred_contrib_log_odds_v1`, `explained_scale: log_odds`, `objective: binary sigmoid:1`. Do not reuse `linear_log_odds` or `boosted_sequential_probability`: their current semantic validators imply different algorithms/scales. Include trusted `model_sha256`, `manifest_sha256`, `feature_version`, ordered `matrix_feature_order_sha256`, `feature_snapshot_digest`, `transaction_id`, `run_id`, `dataset_version`, `context_revision`, and `evidence_digest` bound to canonical content. The digest policy and whether this is attached to an assessment or an immutable sidecar need owner confirmation. The bridge must continue publishing the existing v2 assessment unchanged until a reviewed migration.

Available fields: `status`, `method`, `explained_scale`, `objective`, `num_iteration`, `score`, `raw_score`, `base_value`, `partial: true`, `items` (at most 3), `remainder`, and the identities above. Each item carries source `feature_key`, observed value with unit, signed `contribution` in log odds, and direction derived from its sign. Sort all 11 groups by descending absolute contribution, then ascending feature key for ties; display first 3. `remainder` is the `math.fsum` of all omitted groups. Base is the final native `pred_contrib` entry, never class prevalence. `score` remains the existing native prediction and threshold/status stay unchanged. Reconstruct `raw_score ≈ base_value + sum(items) + remainder`; reconstruct `score ≈ stable_sigmoid(raw_score)` with sigmoid parameter 1 from the model objective. The amount feature is `current_amount_paid_log1p` with unit `log1p(source amount)`; it must not be displayed as source money. Source amount, if separately observed in the transaction, is a distinct fact with currency.

## Contract RED acceptance matrix

1. Accept the exact method/scale/objective/identities, finite base/raw/items/remainder, source-key order, at most three items, and digest bound to the same snapshot/context. A standalone method enum test is deliberately RED today.
2. Reject wrong transaction, run, dataset, feature/model/manifest/order digest, wrong scale or method, stale context revision and altered evidence digest.
3. Reject NaN/inf at every numeric field, wrong 33-value native shape, raw additive error above `1e-8`, score reconstruction error above `1e-12`, or score differing from unchanged scorer above `1e-12`.
4. Test unknown currency and format through their frozen `__UNKNOWN__` buckets. Group **all** one-hot contributions, including inactive buckets; 11 groups must preserve 32-column sum within `1e-8`.
5. Reject incorrect top-3 ranking, omitted-group remainder, direction, observed unit and a log1p amount presented as original money. Preserve score, review status, threshold, old bridge payloads/reports and fixture/rules cases.

Affected consumers after review: producer schema/semantic checks, Feature 003 dataset resolver and outbound projection/notice, evidence path validator, provider context size gate, `web/src/contracts.ts` decoder and case display. The current validator reconstructs `linear_log_odds` specially and otherwise compares the additive sum to probability; it must gain a distinct branch. The existing frontend decoder uses the same assumption. Historical snapshots must remain frozen.

## Reviewed compatibility recommendation pending owner decision

The sidecar's `canonical_transaction_id` is the model's `ibm-hi-small:…:row:…` key; `transaction_id` is the bridge's public `D…` key. `assessment_run_id` is the bridge snapshot `run_bridge_…`, distinct from an investigation `inv_…` run. Bind `case_id`, `dataset_version`, original `context_revision`, trusted model/manifest/order hashes and the existing `sha256:` feature digest. Compute `evidence_digest` over canonical sidecar JSON excluding that digest. Revalidate all bindings and additive/score equations at the join. Fail closed on missing sidecar or mismatch while leaving the original v2 assessment/score available with its existing `unsupported_method` status; do not silently replace it.

After owner approval, a separate case detail/sidecar endpoint can expose the full payload to UI without changing the v2 case decoder. For provider use, join a bounded contribution summary to a *newly generated case-fact evidence item* after the existing `outbound_context` projection; `content_sha256` already binds its exact text/facts and `validate_report` binds the item to attempt and original `context_revision`. The current evidence viewer can show these facts. A dedicated sidecar display needs a separate decoder/view; old cases and archived evidence keep their existing paths. The current provider/case-fact tool code does not perform this join yet.
