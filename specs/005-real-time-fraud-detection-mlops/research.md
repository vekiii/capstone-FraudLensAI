# Research and proposed engineering decisions

**Status:** design comparison only. Repository facts are in [evidence.md](evidence.md); no new service was installed or benchmarked. External primary documentation consulted 15 Nov 2026: [Debezium PostgreSQL connector](https://debezium.io/documentation/reference/connectors/postgresql.html), [Kafka delivery design](https://kafka.apache.org/43/design/design/), [Redpanda compatibility](https://docs.redpanda.com/streaming/current/develop/kafka-clients/), [PostgreSQL replication slots](https://www.postgresql.org/docs/current/runtime-config-replication.html), [dbt incremental models](https://docs.getdbt.com/docs/build/incremental-models), and [MLflow registry](https://mlflow.org/docs/latest/model-registry). These describe product capabilities, not this repository's tested behavior.

| Decision | Alternatives and trade-offs | Proposed choice, repository reason, verification |
|---|---|---|
| Live storage | SQLite is simple and already used for immutable local batch runs; concurrent producer/CDC/worker/API roles and logical CDC call for a server database. | PostgreSQL for new live facts/state/predictions; retain SQLite for batch. Prove transaction boundaries and role permissions in T003–T005/T021. |
| Change capture | Polling risks gaps/high scan load; an application outbox gives an explicit domain event but requires producer changes; CDC directly observes committed inserts but depends on slots/WAL and schema discipline. | Debezium CDC for the proposed PostgreSQL table, with explicit initial-snapshot/LSN gate and slot monitoring. If connector support or permissions fail, revisit outbox as a recorded decision. T008–T009. |
| Broker | Apache Kafka has broad ecosystem support; Redpanda offers a smaller local footprint but protocol compatibility has exceptions. Neither is installed or measured here. | Kafka-compatible contract with Redpanda as a **proposed** local Compose default, pinned/tested before lock-in; Kafka remains an alternative. One partition first. T006–T010. |
| Stream computation | Dedicated Flink/Spark can manage distributed state but adds operational complexity; Python worker fits current code but needs explicit durability/order logic. | One Python worker, PostgreSQL state/checkpoint, measured throughput; no multi-worker claim. T012–T025. |
| State store | In-memory state is fast but crash-prone; separate RocksDB complicates checkpoints; PostgreSQL state can share a transaction with outputs. | PostgreSQL durable buffer/history/checkpoint and atomic output transaction. Validate replay and indexes. T012, T021–T024. |
| ETL/ELT | Reusing online feature state for training risks drift and label coupling; offline SQL can rebuild as-of views and lineage, but must prove parity. | Live Python incremental ETL for scoring; offline SQL/dbt ELT for versioned training with parity tests. dbt `unique_key` alone is not a correctness proof. T033–T035. |
| Artifact/registry | Loading mutable MLflow alias directly simplifies operations but bypasses existing trusted local hash/path checks and makes a switch non-atomic for workers. | Log/register in MLflow, then approve an immutable digest in a deployment record; stage and validate a local artifact with `load_trusted_artifact`, use a separate live adapter. T036–T040. |
| Watermarks/late facts | Unbounded wait preserves order but stalls forever; immediate processing is faster but can corrupt strict-past history; revision/retractions increase complexity. | Proposed 120-second event-time hold, explicit heartbeat, quarantine past-finalization arrivals, audited generation replay. Benchmark latency/late fraction before approval. T013–T014/T023. |
| Delivery claim | Broker exactly-once features do not make PostgreSQL side effects exactly once automatically. | At-least-once delivery plus atomic DB checkpoint/output and unique IDs gives exactly-once **observable** assessment for identical replay. Crash tests and reconciliation prove it; do not claim end-to-end exactly-once transport. T021–T025. |
| Promotion/rollback | Automatic registry alias changes can route an unreviewed model; manual file replacement lacks audit. | Human-reviewed promotion to exact digest plus atomic deployment pointer; rollback to prior digest and generation audit. T037–T040. |

**Unverified:** exact Docker image versions, connector configuration on Windows Docker Desktop, local throughput, WAL consumption, broker client compatibility and model artifact availability. T001, T006, T008 and T045 resolve these with actual observations. The proposed stack is beyond the currently approved MVP; [proposal records](proposals/001-cdc-and-streaming.md) remain pending team decision.

## Additional proposed decisions for Phase 7

No external documentation was consulted for these comparisons. Before lock-in, add dated primary-source links for the chosen vector store, embedding model, LLM provider and each site library. These are design options, not verified choices.

| Decision | Alternatives and trade-offs | Proposed choice, repository reason, verification |
|---|---|---|
| Vector store | pgvector in the existing PostgreSQL keeps one database, one backup and one role model, but needs the extension and adds index load; a local FAISS file is simple and fast but sits outside DB roles and transactions; a dedicated vector database adds another service. | Prefer pgvector if the extension is available in the pinned image, otherwise a versioned local index file referenced from `kb_versions`. Decision (g) at T047; verify under Python 3.14 in T050. |
| Embedding model | A hosted API model is easy but sends text off-host; a local model keeps data in the stack but adds weight and a dependency. | Corpus and queries are synthetic and reviewed, so either is possible; choose at T047 with the data-handling decision (h). Pin the model identity into `kb_versions`. |
| LLM provider | External API gives quality and little setup; a local model avoids external calls but costs hardware and quality; a mock provider is deterministic for tests only. | External calls blocked until decision (h). Use a clearly labelled mock for tests and CI. Record the provider and model identity in `verification_configs`. |
| Verification timing | Inline in the worker's transaction would couple scoring latency and availability to an LLM; a separate polling process after commit isolates failure. | Separate `verifier` process reading committed `alert_decisions`; no shared transaction. Verified by T053 outage test. |
| Verification storage | Writing the verdict onto the prediction or alert row is simple but would mutate immutable rows and mix advisory text with scores; a separate table keeps scores and policy decisions untouched. | Separate `verification_configs` and `verification_runs`, keyed by generation, transaction and config. Verified by T052 byte-identical check. |
| Retrieval design | Dense-only misses exact policy terms; keyword-only misses paraphrase; reranking adds latency. | Hybrid search, top 8, rerank to 4, minimum similarity cut below which the verdict is `uncertain`. Tune on the T054 evaluation set, not on intuition. |
| Confidence reporting | LLM self-reported confidence looks informative but is not calibrated. | Store categorical verdict, citations and retrieval scores only; no confidence number in the contract. |
| Site placement | A separate `web/` app isolates heavy animation and WebGL dependencies from the analyst dashboard; extending `frontend/` reuses the existing build but mixes marketing motion with a working tool. | Separate app by default; decision (j) at T047. The analyst dashboard only gains the T056 evidence panel. |
| Site data | Hard-coded figures drift from the model; generated JSON ties every number to a version and timestamp. | Generated static files plus the FR-010 API, with precomputed fallback. Verified by T058 tests. |
| Motion libraries | Smooth-scroll, a GSAP-style timeline library and three.js reproduce the reference's feel but add bundle weight and licence considerations; CSS-only motion is lighter but cannot do the scroll-driven WebGL story. | Use the reference stack, keep one canvas with a capped pixel ratio and a static fallback, honour reduced motion. Record licences and pinned versions in T057. |

**Unverified for Phase 7:** provider availability and terms, local vector-store compatibility with Python 3.14, retrieval quality on the authored corpus, verification latency and cost, library licences, and site performance. T047, T050, T054, T057 and T059 resolve these with actual observations. The RAG layer and site are beyond the currently approved MVP and remain pending the T047 team decision recorded in [proposal 002](proposals/002-rag-and-showcase.md).
