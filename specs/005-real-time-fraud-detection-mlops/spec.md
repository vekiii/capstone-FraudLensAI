## Problem and outcome

Today, the application imports a local synthetic IBM CSV, builds 24-hour history in SQLite, scores an explicit completed batch run, then serves read-only cases. There is no transaction write API, CDC connector, broker, streaming state, live serving identity, registry or monitoring stack. The goal is a continuously operating **review queue**: an authorized transaction committed in PostgreSQL is captured by CDC, validated from a durable log, scored against point-in-time history by a pinned model, stored with an alert decision, and shown in FastAPI and the dashboard. A separate offline path uses confirmed, delayed investigation outcomes to prepare versioned training data and govern model promotion. A score alone never closes or escalates an account.

**Explanation layer.** After an assessment is persisted, a retrieval-augmented generation (RAG) verifier may attach a *verification record*: it retrieves passages from a versioned knowledge base of fraud typologies and review policies, and an LLM returns `support`, `reject` or `uncertain` with citations to the retrieved passages. The verification is advisory evidence for the analyst. Like the score, it never closes, blocks or escalates an account, never changes the stored score or alert decision, and is stored as a separate, versioned record. A public showcase site (landing, data and model, RAG, live demo) presents the project and reads only generated static data and the read-only live API.

Proposed first version uses one ordered transaction topic partition and one stateful Python worker. This intentionally limits throughput until sender/receiver consistency, late-data semantics and crash recovery are measured. Performance numbers below are **proposed acceptance targets**, not measured properties.

## User stories and acceptance

1. **Ingestor:** I submit a valid synthetic transaction with a stable external ID; one committed fact appears once in the operational ledger. Duplicate ID plus identical facts is idempotent; different facts under the ID are rejected. **AC-01:** database, CDC envelope and broker identity agree.
2. **Analyst:** I see only completed assessments, their model/feature/alert-policy versions, event and processing times, coverage, score and explanation. **AC-02:** one SQL insert eventually yields one persisted assessment and one visible case when the alert policy selects it, without an offline batch CLI.
3. **Operator:** I can restart any connector/worker and replay delivery without duplicate predictions or lost work. **AC-03:** injected crashes before/after database commit preserve identical final state and recover from a durable checkpoint.
4. **Data steward:** I can detect late, malformed or incompatible events and reconcile them without silent history changes. **AC-04:** held events, quarantines and replay decisions are observable and audited.
5. **Model owner:** I can compare a candidate against a frozen protocol and delayed labels, register exact artifact identity, and promote/roll back only with team approval. **AC-05:** live traffic cannot load a mismatched/unreviewed artifact; rollback pins the prior approved digest.
6. **Existing user:** I can still run fixture and Feature 002 batch journeys. **AC-06:** their contracts and outcomes remain compatible.
7. **Analyst (evidence):** For an alerted assessment I can see a RAG verification: verdict, rationale, the retrieved passages it cites, and the knowledge-base, embedding and LLM versions that produced it. **AC-07:** every persisted verification links to exactly one assessment, cites only passages that were retrieved, never alters the assessment's score or alert decision, and a verifier outage leaves assessments persisting normally with a visible "verification unavailable" state.
8. **Reviewer (showcase):** I can open a four-page site that explains what was built (problem, dataset, model, RAG, RAG call) and shows a working demo. **AC-08:** every number on the site comes from generated data files; the demo labels its source (`fixture`, `batch` or `live`), works from precomputed results when the API is down, and states that all data is synthetic.

## Boundaries, dependencies and questions

**In scope:** a local Compose prototype for PostgreSQL, Debezium, Kafka-compatible broker, one Python worker, FastAPI/dashboard live read path, SQL/dbt offline preparation, MLflow tracking/registry, Prometheus/Grafana observability, and recovery/reconciliation tests. Existing batch and fixture flows remain. **Added (†):** a RAG verifier (knowledge-base build, vector index, embedding model, LLM call, verification store) and a four-page showcase web app. **Out of scope:** payment blocking, automatic case disposition, production multi-region HA, unbounded throughput, mandatory Flink/Spark/Feast/Airflow/Kubernetes, new model families, and claims of real-world predictive quality. **Added out of scope (†):** any RAG-driven blocking, closure or escalation; LLM fine-tuning; passing user-entered or free-text data to an LLM; sending real (non-synthetic) data to an external provider; user accounts, CMS or write paths on the site.

Dependencies: team scope approval before implementation; Docker/Compose resources and approved container versions; a reviewed live source contract; a trusted same-hash trained artifact and approved serving decision; appropriate delayed confirmed labels. The original boosted artifact and peer checks for Feature 002 are currently unavailable/blocked in this checkout. Initial integration may use a **synthetic, separately named fixture artifact** to verify the transport/contract path, but may not call that a real model evaluation or activate it for reviewed cases. **Added (†):** approved embedding model, vector store and LLM provider with a recorded data-handling decision; an authored, reviewed knowledge-base corpus (synthetic or public typologies, no confidential policy text); and, until FR-010 exists, fixture and Feature 002 batch results as the demo source. The site and RAG layer must work against fixture and batch data first, so they do not wait on the live path.

Open decisions for T001/T002: (a) named team decision and schedule/benefit for out-of-course services; (b) exact synthetic live transaction producer and ID issuer; (c) whether an approved Feature 002 artifact and its exact dependencies can be transferred and validated; (d) chosen broker distribution and pinned image/client versions after local testing; (e) permitted data retention and access rules. **Added (†), recorded at T047:** (f) separate named team decision, with benefit and schedule impact, for the RAG layer and its out-of-course services; (g) vector store choice (for example pgvector in the existing PostgreSQL or a local index file) and embedding model; (h) LLM provider, model, and whether any external call is permitted for synthetic data; (i) authorship, licensing and review owner of the knowledge-base corpus; (j) whether the showcase site is a separate `web/` app or part of the existing dashboard, and where it is hosted. If any gate fails, stop the dependent implementation task and record the blocker; do not relax validation.
