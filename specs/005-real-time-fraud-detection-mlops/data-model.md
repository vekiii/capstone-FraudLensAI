# Proposed live and offline data model

**Status:** logical design; no PostgreSQL migrations exist. Existing Feature 002 SQLite tables are separate. All IDs below are scoped by `tenant/source_namespace` if multi-source support is approved; v1 uses one declared namespace. Use UTC timestamps with explicit precision; `event_time` is source asserted, `ingested_at` is server recorded, `processed_at` is worker recorded. Never substitute one for another. Exact currency amounts use reviewed `NUMERIC` bounds plus currency strings; no silent FX conversion.

| Table (proposed) | Key and important columns | Integrity, index, retention/lineage |
|---|---|---|
| `live_transactions` | PK `transaction_id`; immutable source namespace, source_event_id, event_fact_digest, event_time, bank-qualified sender/receiver, paid/received amount+currency, optional format, ingested_at | UNIQUE(namespace, source_event_id); same ID/digest retry no-op, changed digest conflict; index `(event_time,transaction_id)`; retain per approved policy. No label column. |
| `ingestion_receipts` | PK `(source_namespace,source_event_id)`; transaction_id FK, digest, received_at, result | Records producer idempotency/conflict without changing fact; no credentials. |
| `stream_positions` | PK `(consumer_group,topic,partition)`; last durable buffered offset, last finalized event time, max_seen_event_time, watermark, generation | Monotonic buffered offset/watermark; database authority for recovery; row locked by single worker. Event-time finalization need not follow offset order. |
| `pending_events` | PK `transaction_id`, UNIQUE(topic,partition,offset); FK transaction; event_time, payload_digest, status | Index `(status,event_time,transaction_id)`; pending until finalized/quarantined. Raw CDC envelope stored only if approved/secured. |
| `historical_events` | PK `(generation,transaction_id)`; FK transaction, event_time, sender/receiver qualified keys, exact amounts/currencies | Index sender/time and receiver/time; only finalized events feed `[t-24h,t)`; retention at least window plus replay horizon or archived reconstructible source. |
| `feature_snapshots` | PK `(generation,transaction_id,feature_version)`; FK transaction; feature JSON, digest, coverage state/start, history cutoff, computed_at | Immutable per generation; ordered 11 keys checked against feature contract; index by event time; no labels. |
| `predictions` | PK `(generation,transaction_id)`; FK snapshot; model_digest, serving_contract_version, score, kind, explanation JSON, model/training lineage, scored_at | One pinned model per generation; retry with identical digest is no-op, changed digest conflicts; score finite in [0,1], explanation digest/reconstruction; immutable. |
| `alert_decisions` | PK `(generation,transaction_id)`; FK prediction; policy_version, alert boolean, threshold/capacity reason, decided_at, case_id | One pinned policy per generation; UNIQUE `(generation,case_id)`; index `(generation,alert,event_time DESC,transaction_id)` for list. Policy revision creates a new generation. |
| `deployment_versions` | PK deployment_id; exact artifact/manifest digest, training dataset/protocol lineage, serving signature, policy version, approved_by/at, status | Staged/approved/retired immutable approval history; alias is metadata only. |
| `active_generation` | PK source_namespace; generation, deployment_id FK, policy_version, changed_at, revision | One atomic active pointer per source namespace; optimistic revision check and rollback audit. |
| `confirmed_labels` | PK `(transaction_id,label_revision)`; FK transaction; outcome, confirmed_at, available_at, reviewer, evidence_ref | Restricted schema/role. Append revisions, never overwrite; training joins only records available before fixed cutoff. Never join in worker/API read path. |
| `processing_failures` | PK failure_id; transaction_id nullable, topic/partition/offset, reason code, first/last seen, state, redacted digest | Unique unresolved event/reason, retry counts, operator audit. No raw account/credential content in logs/DLQ. |
| `replay_jobs` | PK replay_id; source range, reason, old/new generation, model/policy digests, requested/approved actor and time, status, reconciliation digest | New generation rather than in-place rewrite; audit every activation/rollback. |
| `training_dataset_versions` | PK dataset_id; source-range/hash, feature-policy hash, label cutoff, split/protocol hash, dbt/code revision, created_at | Immutable manifest and row/member hashes; stored outputs access-restricted; distinct from model *serving* compatibility version. |

`live_transactions` is the only canonical live fact table CDC captures. `pending_events`, offsets, state, snapshots, prediction and alert rows are mutable/derived operational state with explicit generation; they do not change source facts. `confirmed_labels` is restricted feedback, not part of the inference table or CDC topic. FK constraints, `NOT NULL`, check constraints and scoped uniqueness must be implemented as well as Pydantic/schema validation. A conflicting event ID or digest must fail closed. Retention periods are **open policy decisions** at T002: retain enough broker/WAL/SQL history to satisfy the approved outage and replay horizon; expose a gap if that cannot be met. See [transaction](contracts/transaction-event.schema.json), [prediction](contracts/prediction.schema.json), and [label](contracts/label-feedback-contract.md) contracts.


## Proposed knowledge-base and verification tables (Phase 7)

These are logical design only; no migrations exist (007 and 008 are proposed in T050 and T052). They follow the model's conventions: UTC timestamps, exact numeric types where needed, immutable derived rows and generation-scoped outputs.

| Table (proposed) | Key and important columns | Integrity, index, retention/lineage |
|---|---|---|
| `kb_versions` | PK `kb_version`; corpus content hash, chunker version, embedding model identity, document count, chunk count, built_at, reviewed_by/at, status | Immutable once built. Same corpus hash, chunker and embedding identity gives the same version; any change creates a new row. Retained while any verification cites it. |
| `kb_documents` | PK `(kb_version, doc_id)`; type, title, source, licence, doc_version, reviewed_by, reviewed_on | Licence and reviewer `NOT NULL`. Contains no transaction rows, account identifiers or labels. |
| `kb_chunks` | PK `(kb_version, chunk_id)`; FK to document; chunk text, token count, overlap range, embedding (or vector-store reference), metadata | Index per retrieval design (vector index and keyword index); immutable per version. Chunk IDs are the only valid citation targets. |
| `verification_configs` | PK `config_id`; FK `kb_version`; embedding model identity, LLM identity, prompt version, retrieval parameters, approved_by/at, status | Immutable approval history mirroring `deployment_versions`; a mutable alias alone cannot change what runs. |
| `verification_runs` | PK `(generation, transaction_id, config_id)`; FK `alert_decisions (generation, transaction_id)`; FK `verification_configs`; status (`completed`, `skipped`, `unavailable`), verdict (`support`/`reject`/`uncertain`), rationale, citations, retrieved set with rank and score, query digest, latency by stage, failure reason code, created_at | Check: verdict present only when status is `completed`. Citations must be a subset of the retrieved set (enforced by the validator and asserted by test). Immutable; a rerun with the same key is a no-op; a new config creates a new row. Only rows for alerted, full-coverage assessments can be `completed`. No raw prompt or provider payload stored unless approved and secured. |

`active_generation` gains a nullable `verification_config_id` column (FK to `verification_configs`) so the API reads the verification that matches the active generation and approved config. The change is additive and nullable, so existing rows and the optimistic revision check are unaffected.

**Isolation rules.** The verification tables are derived, advisory state. They are never written by the worker, never joined in the worker's output transaction, and never read by dbt marts, feature computation, evaluation of the scoring model, or any training path (ML-001, ML-006). The `verifier` role has read access to committed `feature_snapshots`, `predictions`, `alert_decisions` and `kb_*`, and write access to `verification_runs` only; the read-only API role gets read on the verification and knowledge-base tables; `confirmed_labels` remains unreadable by the verifier.

**Retention and gaps.** Retention of `verification_runs` follows its parent `alert_decisions` row. A `kb_version` is retained as long as any verification cites it, so every stored citation stays resolvable. If a knowledge-base version must be withdrawn (licence or review failure), mark it `retired`, keep the rows, and show "source withdrawn" beside affected verifications rather than deleting evidence. Retention periods remain open policy decisions recorded at T002 and T047.
