# ADR 002: PostgreSQL state and bounded event-time finalization

**Status:** Proposed; no streaming state implemented. **Context:** [Batch history](../../../backend/src/fraudlens/feature_history.py) sorts complete events, uses `[t-24h,t)` and emits all equal-time peers before updating history. Kafka arrival order need not match event time, and a transfer affects two account histories.

**Decision proposed:** one topic partition/one active worker; durable PostgreSQL `pending_events`, `historical_events`, `stream_positions` and assessment tables. Persist max seen event time and a **proposed** 120-second watermark lag. Finalize only complete timestamp groups strictly before the watermark. Compute each group's features from earlier finalized facts, then add the whole group to history. A future-time skew check prevents a malformed event from advancing the watermark. A quiet stream requires an explicit auditable heartbeat/advance action. Warm-up stays incomplete until a verified continuous preceding 24 hours exists. Late facts past finalization enter quarantine and require operator-approved new-generation replay, not in-place edits.

**Alternatives:** immediate processing gives low latency but violates point-in-time correctness under disorder; infinite buffering preserves order but no bounded delivery; distributed stream processors add state/checkpoint complexity; sender-key partitioning fails receiver consistency. **Consequences/risks:** the proposed 180-second p95 target includes the 120-second hold and leaves limited processing margin. Low-volume streams can stall without an approved heartbeat, and late-event replay may be costly. T013/T045 must measure these effects before accepting NFR-001. **Validation:** synthetic permutation/equal-time/24-hour/currency parity tests; crash point tests; skew/quiet-stream and late-event reconciliation; measured event-time delay distribution and latency on the declared test load.
