## Architecture and behavior

- GET /api/cases delegates to CaseService.list_cases in cases.py. It loads/validates
  the collection, scores via score_case and projects only canonical CaseSummary
  fields, ordered by case_id. Empty input returns exactly {"items":[]}.
- GET /api/cases/{case_id} uses the existing strict CaseId validator and
  CaseService.get_case. It returns a validated CaseDetail, or CaseNotFoundError
  for a well-formed absent ID. List/detail share the same scoring/identity boundary.
- Dependencies resolve settings and scorer from the current app instance.
  create_app accepts optional scorer injection; get_scorer/get_case_service can be
  overridden through FastAPI's normal dependency mechanism.
- No repository reads occur during application creation or health requests.
  Existing fixture-only startup/default APP_MODE and health response are preserved.
- FastAPI response models remain enabled. OpenAPI error responses explicitly use
  the canonical Error model, including 422 instead of the default validation shape.

Error serialization always uses the closed Error/ErrorBody models. Specific
handlers normalize CaseNotFoundError/404, RequestValidationError/422,
FixtureLoadError/CaseScoringError/ResponseValidationError/500 and framework
HTTPException responses. Existing 405 behavior and Allow header are preserved.
No exception text, rejected request values, fixture paths or tracebacks enter
the response.

The standard Starlette server-error serializer provides generic JSON for unexpected
bugs. ServerErrorMiddleware still re-raises after the response; tests prove a
raise_server_exceptions=True client observes the original programming error.
This does not convert bugs into successful/fallback data or bypass validation.
The former broad score_case wrapper was narrowed: only the untrusted adapter call
translates arbitrary adapter exceptions; validation catches ValueError/TypeError.

Application error logs contain fixed events and, where appropriate, exception
class/status only. They omit exception messages, request paths/values and exc_info.
Tests inspect the fraudlens.main logger. The ASGI server's own handling of
re-raised programming errors remains available for server-side diagnosis.
