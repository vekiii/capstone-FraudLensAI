# T234 — explicit local opt-in and controlled failures

`Settings.mode` defaults to `fixture`; only `APP_MODE=model` opts into the pinned
local model and feature paths. `create_app` keeps `FixtureScorer` for existing
case routes and creates the separate model scorer/store only in model mode.
Absent/incompatible inputs make the risk endpoint return a closed 503
`model_unavailable` response, without fixture fallback. Unknown/invalid IDs,
known unscoreable injected records and output mismatch have controlled 404/422,
409 and 503 responses. Error bodies omit paths, row content and exception detail.
The local operator commands and limits are in `README.md`.

The published research feature snapshot contains only eligible train,
validation and test rows. Warm-up and showcase rows are absent. Therefore an
unlisted ID returns 404; the 409 state is exercised when a feature provider
explicitly marks a known record unscoreable. No label-bearing source is opened
to infer eligibility for absent IDs. Fixture startup still requires no ML/data
artifact and imports LightGBM only after explicit model opt-in.

The feature store verifies all three frozen files at initialization and hashes
each file it scans during a lookup before returning a row. This is a simple
local read-only path, not a measured high-throughput serving design; requests
may scan up to all 1,884,981 prepared research rows. No daily capacity or
suppression rule is inferred from it.
