## Exact current path and rejection points

1. [Bridge publisher](../../backend/src/fraudlens/bridge_publish.py) writes each alert's `scored_assessments.assessment_json.explanation` as `unavailable/unsupported_method` with `feature_snapshot_digest="sha256:…"`. [BridgeReader](../../backend/src/fraudlens/bridge_reader.py) pins the manifest and crosswalk and uses a public `D…` transaction ID distinct from the canonical model ID. Its `detail` validates the frozen reviewed producer-v2 schema. Mutating the existing DB would break its pinned hash; the sidecar must be separate.
2. [DatasetReader.resolve](../../backend/src/fraudlens/investigation/dataset.py) reads that assessment, constructs context v2, validates it, checks source/score/method and reconstructs additive explanations. Its sigmoid branch covers only `linear_log_odds`; a new log-odds method would otherwise be compared directly to probability. [context-v2.json](../../specs/003-ai-investigation/contracts/context-v2.json) references the reviewed producer-v2 snapshot, whose `ExplanationAvailable.method` enum lacks the new method; the object is closed. [models.validate](../../backend/src/fraudlens/investigation/models.py) has a closed method→scale map and verifies `context_revision` over the complete context. Replacing the assessment invalidates old revisions and archive binding.
3. [outbound_context](../../backend/src/fraudlens/investigation/context.py) aliases account identities and copies the v2 assessment. `validate_outbound_dataset` builds a closed producer-v2 projection; a new top-level sidecar or new assessment fields fail. Its current available notice describes **sequential boosted probability** and would misdescribe native `pred_contrib`. [OpenAIProvider.project_conversation](../../backend/src/fraudlens/investigation/provider.py) accepts only `source_mode,notice,context_revision,case_id,transaction,assessment[,context_contract_version]` and revalidates dataset projection. A direct added `contribution_summary` field fails `provider_input_invalid` (targeted test observed this).
4. [ToolExecutor._case](../../backend/src/fraudlens/investigation/tools.py) gets the validated outbound body, makes a `case_fact` Evidence item with `text` and exact `facts`, and binds `content_sha256`. History/procedure tools are separately bounded at 16,000 bytes. [validation._evidence](../../backend/src/fraudlens/investigation/validation.py) binds evidence to attempt/context revision, checks digest and exact assertion paths; stored reports cite evidence IDs. A sidecar can join only after verifying its own identities/digest, then create a **new** case-fact evidence item for a new attempt. Old evidence and reports must not be rewritten. The generic investigation evidence decoder/view already accepts a `case_fact` item's text/path/value facts; no new evidence kind is required.
5. [web/src/contracts.ts](../../web/src/contracts.ts) rejects the new method, extra `raw_score`/identity fields in its closed v2 explanation, and applies sigmoid only to `linear_log_odds`. [Cases.tsx](../../web/src/pages/Cases.tsx) displays v2 method/scale/base/remainder/items but has no raw-margin or new-method wording. A separate sidecar endpoint and decoder/view can be added after review, leaving v2 case decoding intact. [web/src/investigation/contracts.ts](../../web/src/investigation/contracts.ts) and `views.ts` accept/display bounded generic evidence facts; adding a new evidence kind or changing old report shape is unnecessary.

## Contract options

| Option | Required changes | Preservation |
|---|---|---|
| Separate immutable `local-contribution-sidecar-v1` keyed to existing bridge/context | New pinned sidecar manifest/index and binding validator; optional new case endpoint/decoder; new-attempt case-fact projection and 48,000-byte guard tests | Existing bridge bytes, assessment v2, context revision, old reports and evidence unchanged. **Recommended.** |
| Assessment/context v3 with new method | New producer/assessment/context schemas, resolver, semantic reconstruction, context digest, outbound/provider projection, case API/frontend decoding, migration/archive rules | Possible only with explicit dual-version handling; larger migration and stored-context risk. Defer. |

The recommendation is a **proposal** for Feature 003 owner review. [Example](../../specs/003-ai-investigation/contracts/examples/local-contribution-sidecar-v1.proposal.json) contains an actual verified browser case's existing aliased v2 provider context plus separate v1 sidecar. It distinguishes `canonical_transaction_id` (model) from public `transaction_id` (`D…`), `assessment_run_id` (`run_bridge_…`) from investigation run (`inv_…`), and preserves the bridge's `sha256:` feature digest. The sidecar's `evidence_digest` is SHA-256 of canonical sorted compact JSON excluding that field. The isolated [proposal validator](../../backend/tests/proposals/local_contribution_sidecar.py) checks exact identities, order, scale, top-three, remainder, finite values, reconstruction and digest against the original inputs. It is **not** production code or an approved wire schema. Missing/mismatched sidecar should fail closed for contributions while the existing v2 score remains available; no fixture fallback.
